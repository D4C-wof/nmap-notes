# 04 · 端口扫描：技术选型与结果判读

> **本章目标**：知道六种端口状态分别意味着什么，以及六种扫描技术在什么条件下该用哪一种。
>
> 这是全书最长、也最该读透的一章。**看不懂端口状态，后面所有章节都是背命令。**

## 4.1 六种端口状态

Nmap 把每个端口归入六种状态之一。判断依据是"目标回了什么包"，而不是"端口有没有服务"。

| 状态 | 含义 | 目标回了什么 | 常见成因 |
| --- | --- | --- | --- |
| `open` | 端口开放，有服务在监听 | SYN/ACK（TCP）或应用层响应（UDP） | 服务正常运行 |
| `closed` | 端口关闭，主机可达 | RST（TCP）或 ICMP port unreachable（UDP） | 主机在，但没人监听该端口 |
| `filtered` | **无法判断**，探测包被丢弃 | **什么都没回** | 防火墙 DROP、路由器 ACL、IPS 静默拦截 |
| `unfiltered` | 端口可达，但开/关未知 | RST，但来自 `-sA` 这类不判断开关的扫描 | 防火墙放行，但扫描技术本身不区分 open/closed |
| `open\|filtered` | 开放或被过滤，二者无法区分 | 什么都没回 | UDP 扫描、FIN/NULL/Xmas 扫描的典型结果 |
| `closed\|filtered` | 关闭或被过滤，二者无法区分 | 什么都没回 | 极少数场景（如 IP ID 空闲扫描），日常少见 |

### 4.1.1 判读要点

**`filtered` 是最容易被误读的状态。** 它不代表"没有服务"，只代表"我没拿到任何回应"。三种完全不同的情况都会产生 `filtered`：

1. 防火墙 DROP 了包 → 真的被过滤；
2. 目标主机不存在（配合 `-Pn` 时）→ 包到了虚空；
3. 你的出口网络拦了包 → 你根本发不出去。

**区分方法**：换一种探测方式再试。如果 `-sS` 是 `filtered`、`-sA` 变成 `unfiltered`，说明包能到、只是 SYN 被拦——防火墙在工作，主机也活着。

**`open|filtered` 的成因**：UDP 和 FIN/NULL/Xmas 扫描在"没回应"时无法区分"端口开着但服务不回包"与"包被防火墙丢了"。RFC 规定这两种情况下的行为一致，所以 Nmap 只能给个合并状态。

### 4.1.2 状态判定速查

| 扫描技术 | 收到 SYN/ACK | 收到 RST | 无回应 |
| --- | --- | --- | --- |
| TCP SYN (`-sS`) | `open` | `closed` | `filtered` |
| TCP Connect (`-sT`) | `open` | `closed` | `filtered` |
| TCP ACK (`-sA`) | — | `unfiltered` | `filtered` |
| TCP FIN/NULL/Xmas | — | `closed` | `open\|filtered` |
| UDP (`-sU`) | — | — | `open\|filtered` |

> 注意 `-sA` 那一行：ACK 扫描**永远不告诉你端口开不开**，它只回答"这个端口有没有被防火墙挡"。这是它唯一的用途。

## 4.2 六种扫描技术

### 4.2.1 `-sS`：TCP SYN 扫描（半开扫描）

#### 命令

```bash
nmap -sS -p <端口列表> <目标IP>
```

#### 适用场景

- **默认首选**的 TCP 扫描方式；
- 有 root/管理员权限；
- 想快、想相对隐蔽。

#### 原理

```text
你  --SYN-------->  目标:端口
你  <----SYN/ACK--  目标   → 端口 open
你  --RST-------->  目标   → 立刻断开，不完成三次握手
```

因为**从不完成三次握手**，应用层不会记录一条完整连接日志。这是它被称为"半开扫描"的原因。

#### 示例

```bash
sudo nmap -sS -p 22,80,443 192.0.2.10
```

#### 示例输出

【待补充示例输出】建议补充：对本地靶场执行 `-sS -p 22,80,443` 的完整输出，要求至少包含一个 `open`、一个 `closed`，用于说明 `STATE` 列与 `REASON` 列（配合 `--reason`）。

#### 结果判读

| 状态 | 判读 |
| --- | --- |
| `open` | 有服务监听，进 [05 章](05-service-os.md) 做版本探测 |
| `closed` | 主机在，端口没服务 |
| `filtered` | 换 `-sA` 验证是防火墙还是包丢了 |

配合 `--reason` 能看到判定依据（`syn-ack` / `reset` / `no-response`），这是排错时最有用的信息。

#### 注意事项

| 项 | 说明 |
| --- | --- |
| 权限 | **需要 root / 管理员**（原始套接字）。普通用户会报 `You requested a scan type which requires root privileges` |
| 隐蔽性 | 比 `-sT` 隐蔽，但**远谈不上"不被发现"**。现代 IDS/防火墙对 SYN 扫描的检测非常成熟 |
| 无状态防火墙 | 对只做包过滤的设备有效；对有状态检测（SPI）的防火墙，半开连接同样会被记录 |
| 不影响服务 | 正常情况下不会让服务崩溃，但极少数老旧设备对异常 SYN 敏感 |

#### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 大量 `open` | `-sV -p <端口列表>` 识别版本 |
| 大量 `filtered` | `-sA` 判断防火墙策略；或 `--reason` 看原因 |
| 报权限错误 | 加 `sudo`，或退而用 `-sT` |

### 4.2.2 `-sT`：TCP Connect 扫描（全连接）

#### 命令

```bash
nmap -sT -p <端口列表> <目标IP>
```

#### 适用场景

- **没有 root 权限**时唯一可靠的 TCP 扫描方式；
- 通过某些代理（如 SOCKS）扫描时，只能用这种方式；
- 想确认"应用层能不能真的建立连接"。

#### 原理

调用操作系统的 `connect()` 系统调用，**完整走完三次握手**：

```text
你  --SYN-------->  目标
你  <----SYN/ACK--  目标
你  --ACK-------->  目标   ← 连接建立成功
你  --RST/FIN---->  目标   ← 立即关闭
```

#### 示例

```bash
nmap -sT -p 22,80,443 192.0.2.10
```

#### 示例输出

【待补充示例输出】建议补充：同一目标分别用 `-sS` 与 `-sT` 扫描的输出对比，说明**端口表完全一致**，差异只在速度与目标侧日志中。

#### 结果判读

端口状态判定与 `-sS` 相同（`open` / `closed` / `filtered`）。区别在**目标侧**：

| 对比项 | `-sS` | `-sT` |
| --- | --- | --- |
| 权限 | 需要 root | 不需要 |
| 速度 | 快 | 较慢（每次都要建立完整连接） |
| 目标侧日志 | 通常只有半开记录 | 应用日志、`netstat`、WAF 都会留下完整连接 |
| 被检测概率 | 中 | 高 |
| 通过代理 | 不支持 | 支持 |

#### 注意事项

> [!WARNING]
> `-sT` 会在目标的应用日志、WAF、IDS 里留下**大量完整连接记录**。在真实客户环境中，这可能直接触发安全运营告警并追到你。它"合法可用"不等于"不会被发现"。

- 全连接会消耗目标的一个连接名额（backlog）。对连接数受限的服务（如老式嵌入式设备），高频 `-sT` 可能导致**服务短暂无法响应新连接**。
- 非 root 环境下，`-sS` 会被 Nmap 自动降级为 `-sT`，并提示 `TCP connect() scan`。

#### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 有 root 但想更隐蔽 | 换 `-sS` |
| 无 root | 保持 `-sT`，同时降低速率 `-T2` |
| 结果与 `-sS` 不一致 | 大概率是中间设备对半开连接做了特殊处理，以 `-sT` 结果为准更接近"真实可用性" |

### 4.2.3 `-sU`：UDP 扫描

#### 命令

```bash
nmap -sU --top-ports 50 <目标IP>
```

#### 适用场景

目标可能提供 UDP 服务：DNS(53)、SNMP(161)、NTP(123)、DHCP(67/68)、TFTP(69)、Syslog(514)、mDNS(5353)、IPsec(500/4500)。

#### 原理

UDP 无连接，判定靠"有没有 ICMP 端口不可达"：

```text
你  --UDP包------>  目标:端口
    ← ICMP port unreachable    → closed
    ← 应用层响应               → open
    ← 什么都没有               → open|filtered   ← 无法区分
```

#### 示例

```bash
sudo nmap -sU --top-ports 50 192.0.2.10
```

#### 示例输出

【待补充示例输出】建议补充：对一台开着 DNS(53/udp) 的本地靶机执行 `-sU --top-ports 50`，展示 `open`（有响应）与 `open|filtered`（无响应）
在同一张表里并存的样子。这是理解 `open|filtered` 最直观的例子。

#### 结果判读

| 状态 | 含义 | 该怎么做 |
| --- | --- | --- |
| `open` | 有 UDP 服务响应 | 进 `-sV -sU` 做版本探测 |
| `open\|filtered` | 开或被过滤，无法区分 | **不要急着报"开放"**，这是最常见的误报来源 |
| `closed` | 收到 ICMP 端口不可达 | 无服务 |
| `filtered` | 收到 ICMP 管理禁止类消息 | 被防火墙拦 |

#### 注意事项

> [!WARNING]
> **UDP 扫描是全 Nmap 最慢的扫描。** Nmap 必须为每个端口等待超时或 ICMP 回应。扫 1000 个 UDP 端口，可能要几十分钟。
>
> 务实用法：**先 `--top-ports 50`，只对感兴趣的端口做 `-sU -p <端口>`**，并显式加 `--max-retries 1` 与 `--host-timeout`。

| 项 | 说明 |
| --- | --- |
| 权限 | 需要 root（要收 ICMP） |
| 速度 | 极慢，建议配 `-T4` 或 `--min-rate` |
| 误报 | `open\|filtered` 不能直接当"开放"写进报告 |
| 版本探测 | 要 `-sV` 与 `-sU` **同时**给，单独 `-sV` 不探 UDP |

#### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 出现 `open\|filtered` 且你怀疑真有服务 | 用针对该服务的 NSE 脚本验证（如 `--script snmp-info`），而不是靠扫描状态猜 |
| UDP 扫不动 | 缩小到具体端口：`-sU -p 53,123,161` |
| 想确认 SNMP | `-sU -p 161 -sV`，注意 SNMP 可能暴露大量设备信息 |

### 4.2.4 `-sA`：TCP ACK 扫描（探测防火墙）

#### 命令

```bash
nmap -sA -p <端口列表> <目标IP>
```

#### 适用场景

**不用于发现开放端口**，只用于回答一个问题：*这个端口有没有被防火墙挡？*

#### 原理

ACK 包不属于任何已有连接，主机收到后按 RFC 应该回 `RST`：

```text
你  --ACK-------->  目标:端口
    ← RST           → unfiltered（包到了，主机活着）
    ← 无回应        → filtered  （包被丢了）
```

**关键点：回 `RST` 说明包能穿透到主机，但完全不能说明端口开没开。**

#### 示例

```bash
sudo nmap -sA -p 22,80,443 192.0.2.10
```

#### 示例输出

【待补充示例输出】建议补充：对一台"有状态防火墙只放行 443"的靶机，先 `-sS`（80 显示 filtered）、再 `-sA`（80 显示 unfiltered 或 filtered）
的对照输出，用于说明两种状态组合如何推断防火墙规则。

#### 结果判读

| `-sS` 结果 | `-sA` 结果 | 推断 |
| --- | --- | --- |
| `open` | `unfiltered` | 端口开，无拦截 |
| `closed` | `unfiltered` | 端口关，无拦截 |
| `filtered` | `filtered` | 该端口/该方向被 DROP |
| `filtered` | `unfiltered` | **包能到主机，但 SYN 被单独拦了**——典型的"只拦新建连接"策略 |

最后一行是 `-sA` 的核心价值：它把"完全打不通"和"能通但被策略拦"区分开了。

#### 注意事项

| 项 | 说明 |
| --- | --- |
| 不判断开关 | 所有 `unfiltered` 的端口都不代表开放，**不要写进开放端口清单** |
| 权限 | 需要 root |
| 有状态防火墙 | 对有 SPI 的防火墙，ACK 可能被直接丢弃，得到全 `filtered`，此时该方法失效 |
| 目标可能是路由器 | 有些设备对所有 ACK 都回 RST，结果全 `unfiltered`，无信息量 |

#### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 大量 `unfiltered` + `-sS` 全 `filtered` | 说明有应用层/新建连接拦截，考虑 `--source-port` 或由客户提供白名单出口 |
| 全部 `filtered` | 出口被封或有状态防火墙全拦，进 [09 章](09-troubleshooting.md) |
| 想进一步看规则 | 不要继续猜，找客户要防火墙策略文档；主动探测规则边界属于高风险行为 |

### 4.2.5 `-sN` / `-sF` / `-sX`：NULL / FIN / Xmas 扫描

#### 命令

```bash
nmap -sN -p <端口列表> <目标IP>
nmap -sF -p <端口列表> <目标IP>
nmap -sX -p <端口列表> <目标IP>
```

#### 适用场景

**仅在特定条件下有效**：目标是老式 Unix 系统、中间是无状态包过滤防火墙。现代环境（Windows、有状态防火墙、云安全组）下**基本不工作**。

#### 原理

利用 RFC 793 的一个历史行为：**关闭的端口收到不带 SYN/RST/ACK 标志的包，会回 `RST`；开放的端口会忽略它**。

| 技术 | 发送的 TCP 标志位 | 昵称 |
| --- | --- | --- |
| `-sN` | 全 0（无标志） | NULL 扫描 |
| `-sF` | 只有 FIN | FIN 扫描 |
| `-sX` | FIN + PSH + URG | Xmas 扫描（"点亮圣诞树") |

判定：

| 回应 | 状态 |
| --- | --- |
| `RST` | `closed` |
| 无回应 | `open\|filtered` |

#### 示例

```bash
sudo nmap -sF -p 22,80,443 192.0.2.10
```

#### 示例输出

【待补充示例输出】建议补充：在一台 Linux 靶机上执行 `-sF` 与 `-sS` 的对照输出——预期 `-sF` 会把开放端口显示为 `open|filtered`，这就是它"看起来没用"的直观证据。

#### 结果判读

| 状态 | 含义 |
| --- | --- |
| `closed` | 确实关闭（收到 RST） |
| `open\|filtered` | **可能是开，也可能被过滤**——无法区分，这就是该技术的主要缺陷 |

#### 注意事项

> [!WARNING]
> 这三种扫描在**现代环境中大概率给出误导性结果**。它们的价值是"绕过只检查 SYN 标志位的无状态防火墙"，而不是"更隐蔽的通用扫描"。
>
> 另外，很多 IDS 把 NULL/FIN/Xmas 扫描视为**明确的攻击特征**（比 SYN 扫描更可疑），隐蔽性宣传与实际相反。

| 项 | 说明 |
| --- | --- |
| 对 Windows | **完全无效**。Windows 对所有这类包一律回 RST，结果全是 `closed` |
| 对有状态防火墙 | 无效，多数直接丢弃 |
| 权限 | 需要 root |
| 与主机发现混淆 | 注意别把 `-sN` 当成 `-sn` 的笔误——`-sN` 会真的扫端口 |

#### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 全 `closed` | 大概率目标是 Windows 或有状态防火墙，**放弃该技术**，回 `-sS`/`-sT` |
| 全 `open\|filtered` | 无信息量，换技术 |
| 想验证防火墙类型 | 这个判断需要更多信息，不要靠单一扫描下结论 |

## 4.3 端口范围与顺序

### 4.3.1 `-p <端口列表>`

#### 命令

```bash
nmap -p <端口列表> <目标IP>
```

#### 适用场景

已知要看的端口（比如已经扫出 22、80、443，只想深入这三个）。

#### 示例

```bash
nmap -sV -p 22,80,443,8080 192.0.2.10

# 范围写法
nmap -p 1-1024 192.0.2.10

# 混合写法
nmap -p 22,80,8000-8100 192.0.2.10

# 按服务名指定（Nmap 会查 services 文件转成端口号）
nmap -p http,https,ssh 192.0.2.10
```

#### 示例输出

【待补充示例输出】建议补充：`-p 22,80,443` 的输出，重点展示表格里**只出现指定的三个端口**，其他端口（无论开关）都不列出——这是 `-p` 与 `-F` 的关键差异。

#### 结果判读

输出表格只包含你指定的端口。**没有出现的端口不是"不存在"，只是"没扫"**。

#### 注意事项

- 端口号不要超过 65535，否则 Nmap 报错退出。
- `-p http` 这种服务名写法依赖系统的 `/etc/services`，跨平台可能不一致，**脚本里建议一律用数字**。
- 想排除某几个端口：`--exclude-ports 22,3389`（与 `-p` 配合）。

#### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 想让 Nmap 帮忙补全信息 | 加 `-sV`（只对这几个端口做，很快） |
| 想确认没有遗漏 | 回到 `-p-` 全端口，别靠 `-p` 猜 |

### 4.3.2 `-p-`：全端口扫描

#### 命令

```bash
nmap -p- <目标IP>
```

#### 适用场景

- 目标很关键，怀疑服务藏在非标准高位端口；
- 前一轮 `-F` / 默认 1000 端口的结果"太干净"，不正常。

#### 示例

```bash
# 全端口 + 跳过探活 + 提速（对已知存活的单台主机）
nmap -Pn -p- -T4 --min-rate 1000 192.0.2.10
```

#### 示例输出

【待补充示例输出】建议补充：`-p-` 在单台本地靶机上的完整输出（65535 行端口不会全部打印，只打印有状态的），用于说明"输出行数远小于 65535"。

#### 结果判读

- 全端口扫 65535 个 TCP 端口，单台主机在局域网内通常几分钟到十几分钟；跨公网可能更久。
- 输出只列出 `open` / `closed` / `filtered` 中的非默认项——实际上默认只显示 `open`、`open|filtered`、
  `unfiltered`（`closed` 需要 `--reason` 或 `-v` 才显示）。
- **判断"全端口扫完了"**：结尾 `Nmap done: 1 IP address (1 host up) scanned in <秒>`，且没有 `Warning: ...` 中断提示。

#### 注意事项

> [!WARNING]
> `-p-` 对**一个网段**使用 = 数百万个包。这已属于大规模扫描，很多 IDS/WAF 会直接封 IP，云厂商安全组也可能触发告警。**只对单台已确认存活、且在授权范围内的主机使用。**

| 项 | 说明 |
| --- | --- |
| 耗时 | 单机分钟级，网段级不可接受 |
| 建议搭配 | `-T4`、`--min-rate`、`-n`、`--open` |
| 输出体积 | 用 `-oA` 保存，别指望终端滚动回看 |
| 合规 | 全端口扫描的"侵入性"明显高于常见端口扫描，授权书里最好写明 |

#### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 扫出高位端口 | `-sV -p <新发现的端口>` 识别服务 |
| 扫了很久没结束 | `Ctrl+C`，改用分批：`-p 1-10000`、`-p 10001-20000` |
| 想只保留有结果的 | 加 `--open` |

### 4.3.3 `-F`：快速扫描

#### 命令

```bash
nmap -F <目标IP>
```

#### 适用场景

**第一次接触一个目标时的默认动作。** 只扫 Nmap 内置的 100 个最常见端口。

#### 示例

```bash
nmap -F 192.0.2.10
```

#### 示例输出

【待补充示例输出】建议补充：`-F` 与默认扫描（不带参数，1000 端口）对同一目标的输出对比，说明 `-F` 只输出 100 端口范围内的结果。

#### 结果判读

- 快（通常几秒到几十秒）；
- **覆盖面只有 100 个端口**，漏报率高；
- 结尾的 `Nmap done` 不会告诉你"只扫了 100 个"，要自己记住。

#### 注意事项

`-F` 与 `--top-ports 100` 大致等价，但**不完全相同**：`-F` 用的是 Nmap 内置的高频端口列表，`--top-ports` 按频率排名取前 n 个。日常用哪个都行。

#### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 只扫出 1–2 个端口，目标看起来"太干净" | 上 `-p-` 全端口 |
| 扫出常规端口 | 直接 `-sV` |

### 4.3.4 `--top-ports <n>`

#### 命令

```bash
nmap --top-ports <n> <目标IP>
```

#### 适用场景

想在"100 个"和"65535 个"之间取一个折中值，比如 1000 或 2000。

#### 示例

```bash
nmap --top-ports 1000 <目标IP>
```

#### 示例输出

【待补充示例输出】建议补充：`--top-ports 1000` 的输出，并在正文说明"1000 个端口不等于 1000 行输出，多数行是 closed 不显示"。

#### 结果判读

`<n>` 是"按出现频率排名的前 n 个端口"，不是"端口号前 n 个"。所以 `--top-ports 1000` 会包含 8080、8443 这类高位端口，但不会包含 1–1000 的全部。

#### 注意事项

- `<n>` 超过 65535 无意义。
- Nmap 的频率数据来自互联网扫描统计，**对你所在的内网不一定适用**（内网常见 3389、445、6379；公网统计里这些排名不同）。
- 内网扫描时，用 `-p` 显式列出内网高频端口，往往比 `--top-ports` 命中率更高。

#### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 内网目标 | 用自定义端口列表：`-p 22,80,135,139,443,445,1433,3306,3389,6379,8080` |
| 公网目标 | `--top-ports 1000` 合理 |

### 4.3.5 `-r`：按顺序扫描

#### 命令

```bash
nmap -r -p <端口列表> <目标IP>
```

#### 适用场景

- 想固定扫描顺序便于对比两次结果；
- 某些老旧设备对乱序端口访问敏感；
- 教学演示时想看"端口一个个被扫"的过程。

#### 示例

```bash
nmap -r -p 1-1000 192.0.2.10
```

#### 示例输出

【待补充示例输出】建议补充：`-r -p 1-100` 与 `-p 1-100`（默认随机）两次输出的端口行顺序对比，证明前者严格升序。

#### 结果判读

输出端口按编号升序排列。**默认情况下 Nmap 会随机化端口顺序**（`--randomize-hosts` 是随机主机，端口随机是默认行为的一部分），目的是避免被基于顺序的检测规则识别。

#### 注意事项

- `-r` **降低隐蔽性**：顺序扫描是 IDS 最容易识别的模式。
- 它与 `--randomize-hosts`（随机化主机顺序）是两个不同维度，别混。

#### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 需要对比两次扫描 | 两次都用 `-r`，结果才好 diff |
| 想更隐蔽 | 去掉 `-r`，让它随机 |

## 4.4 扫描技术选型决策表

| 你的处境 | 用哪个 | 理由 |
| --- | --- | --- |
| 有 root，要扫 TCP | `-sS` | 最快、最常用 |
| 无 root | `-sT` | 唯一可行 |
| 要通过代理 | `-sT` | 原始套接字走不了代理 |
| 要扫 UDP | `-sU --top-ports 50` | 别一上来扫全部 |
| 想知道防火墙挡了哪些端口 | `-sA` | 它只回答这个问题 |
| 目标是老式 Unix + 无状态防火墙 | `-sF` / `-sN` / `-sX` | 唯一有效场景 |
| 目标是 Windows | 不要用 `-sF/-sN/-sX` | 全部误判为 closed |
| 想一次拿全 TCP 端口 | `-p-` | 只对单机用 |
