# 05 · 服务版本与操作系统识别

> **本章目标**：从"这个端口开着"推进到"这个端口上跑的是什么东西、哪个版本、什么系统"。
>
> 这是从"端口表"到"可行动信息"的关键一步。但也要记住一句话：**版本识别是猜测，不是断言。**

## 5.1 为什么需要版本探测

只看端口号会得出错误结论：

| 端口 | 你以为 | 实际可能是 |
| --- | --- | --- |
| 80 | Web 服务器 | 任何东西。运维把 SSH 改到 80 也很常见 |
| 22 | SSH | 某个内部管理协议，或已关闭只剩防火墙规则 |
| 8080 | Tomcat | Jenkins、Nexus、代理、自定义服务 |
| 443 | HTTPS | 任何 TLS 封装的服务 |

**端口号只说明"惯例"，不说明"事实"。** `-sV` 才是问事实。

## 5.2 `-sV`：服务版本探测

### 命令

```bash
nmap -sV -p <端口列表> <目标IP>
```

### 适用场景

- 已扫出开放端口，想知道具体软件与版本；
- 要判断"这个版本有没有已知 CVE"（下一步）；
- 写资产报告需要软件清单。

### 原理

对一个已确认开放的端口，Nmap 会：

1. 建立连接，**发一串精心构造的探测包**（probe）；
2. 把返回的 banner / 响应与内置的 `nmap-service-probes` 指纹库比对；
3. 提取服务名、产品名、版本号、额外信息（主机名、模块名等），生成 `Service Info` 行。

所以 `-sV` 是**主动交互**，不是被动读取 banner。它会产生真实的应用层日志。

### 示例

```bash
sudo nmap -sV -p 22,80,443 192.0.2.10
```

### 示例输出

【待补充示例输出】建议补充：对一个跑着 Web + SSH 的本地靶机执行 `-sV -p 22,80,443` 的完整输出，要求展示 `VERSION` 列（如 `<产品名> <版本>`）、
服务名后的括号备注（如 `(protocol 2.0)`）、以及表下的 `Service Info:` 行。

输出形态：

```text
PORT    STATE SERVICE  VERSION
22/tcp  open  ssh      <产品名> <版本>(protocol 2.0)
80/tcp  open  http     <产品名> <版本>
443/tcp open  ssl/http <产品名> <版本>
Service Info: OS: Linux; CPE: cpe:/o:linux:linux_kernel
```

> 上面是**结构示意**，`<产品名> <版本>` 位置必须由你自己扫描后填入。原文中出现的 `Apache httpd 2.4.49`、`OpenSSH 8.2p1` 是原作者举例，已改为占位符，避免被误读为实测结果。

### 结果判读

| 你看到 | 含义 | 可信度 |
| --- | --- | --- |
| `ssh` + 具体产品/版本 | 指纹匹配成功 | 高 |
| `http` + 产品名但版本缺失 | 认出了产品，版本没抓到 | 中 |
| `unknown` | 指纹库没匹配上 | 无 |
| 服务名带 `?`（如 `http?`） | 猜测，未确认 | 低 |
| 协议明显错乱（如 443 显示 `telnet`） | 指纹误判，需要人工介入 | 极低 |
| `ssl/http` | TLS 封装下的 HTTP | 中高 |

**判读三原则**：

1. **`Service Info` 行比 `VERSION` 列更可信**，它来自多轮探测的交叉验证。
2. **版本号可能不准**：反向代理、负载均衡、WAF 都会改写 banner。看到 `nginx` 不代表后端是 nginx，只代表最外层是。
3. **CPE 是给工具读的**，形如 `cpe:/a:vendor:product:version`，可以直接拿去查漏洞库。

### 注意事项

| 项 | 说明 |
| --- | --- |
| 权限 | 不需要 root（但需要能建 TCP 连接） |
| 速度 | 比纯端口扫描慢很多——每个开放端口要跑多轮探测 |
| 日志 | **会在目标应用日志里留下 HTTP 请求、TLS 握手等记录**，可能触发 WAF |
| 精度 | 默认强度（intensity 7）在速度与准确度之间取平衡 |
| 不要扫全端口 | `-sV -p-` 会让 65535 个端口每个都跑探测，极慢。**先 `-p-` 找端口，再 `-sV -p <结果>`** |

### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 版本清晰 | 记录下来，去官方漏洞库核对影响范围（这一步在本书之外，注意别在未授权环境做验证） |
| `unknown` 或明显误判 | 加 `--version-all` 深度探测 |
| 服务跑在非标准端口且没识别出来 | 加 `--allports` |
| 只想快速看一眼 | 用 `--version-light` |

## 5.3 版本探测强度：`--version-light` / `--version-all`

### 5.3.1 `--version-light`

#### 命令

```bash
nmap -sV --version-light -p <端口列表> <目标IP>
```

#### 适用场景

目标多、时间紧，只需要"大概是 nginx 还是 IIS"这个级别。

#### 示例

```bash
nmap -sV --version-light -F 192.0.2.10
```

#### 示例输出

【待补充示例输出】建议补充：同一目标 `--version-light` 与默认 `-sV` 的对照输出，展示前者更容易出现"产品名有、版本号空"的情况。

#### 结果判读

`--version-light` 等价于 `--version-intensity 2`：只发最有可能匹配的少量探测包。

| 对比 | `--version-light` | 默认 `-sV` | `--version-all` |
| --- | --- | --- | --- |
| 强度 | 2 | 7 | 9 |
| 速度 | 最快 | 中 | 最慢 |
| 准确度 | 中低 | 中高 | 最高 |
| 日志痕迹 | 少 | 中 | 多 |
| 适用 | 大批量初筛 | 常规使用 | 疑难目标 |

#### 注意事项

- 轻量探测**不会尝试 SSL 相关探测**，所以 443 端口常只给出 `ssl/http` 而无版本。
- 它不是"更安全"的选项——只是"更少探测"，日志少一些，但识别不了就是识别不了。

#### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 版本为空 | 对该端口单独跑默认 `-sV` 或 `--version-all` |

### 5.3.2 `--version-all`

#### 命令

```bash
nmap -sV --version-all -p <端口列表> <目标IP>
```

#### 适用场景

- 默认 `-sV` 给 `unknown`；
- 服务被 WAF / 反代伪装，需要多轮探测交叉验证；
- 目标是很重要的资产，值得多花时间。

#### 示例

```bash
sudo nmap -sV --version-all -p 8080 192.0.2.10
```

#### 示例输出

【待补充示例输出】建议补充：一个默认 `-sV` 返回 `unknown`、加 `--version-all` 后识别出产品的真实案例输出（可用本地靶场 + 自定义 banner 构造）。

#### 结果判读

`--version-all` 等价于 `--version-intensity 9`：**尝试全部探测包**。

- 时间可能翻几倍；
- 可能把本来 `unknown` 的端口识别出来；
- 也可能**产生更多误判**——探测越多，错误指纹匹配的机会越大。

#### 注意事项

> [!WARNING]
> `--version-all` 会向目标发送大量不同类型、不同格式的请求。在有 WAF 的环境里，这是**最容易被判定为扫描行为**的操作之一。生产环境慎用，用前确认授权范围允许。

#### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 还是 `unknown` | 手工验证：`curl -I`、`nc`、`openssl s_client`，或直接看 `-sC` 的脚本输出 |
| 认出来了但版本可疑 | 记 `【待核实】`，别当定论写进报告 |

### 5.3.3 `--allports`：不要跳过任何端口

#### 命令

```bash
nmap -sV --allports -p <端口> <目标IP>
```

#### 适用场景

服务跑在**非标准端口**上（比如 SSH 在 22222），而 Nmap 因为"这个端口号通常是别的服务"而没做完整探测。

#### 示例

```bash
nmap -sV --allports -p 22222 192.0.2.10
```

#### 示例输出

【待补充示例输出】建议补充：同一台把 SSH 改到高位端口的靶机，`-sV` 与 `-sV --allports` 的输出对照。

#### 结果判读

默认情况下，Nmap 为了提高速度，会**跳过一些明显的排除性端口探测**（比如 9100 打印机端口不做 SSL 探测）。`--allports` 关闭这个优化，对所有端口一视同仁。

#### 注意事项

- 会显著变慢；
- 与 `-p-` 组合是灾难（65535 个端口 × 全部探测）；
- 通常只需要对**个别端口**使用。

#### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 高位端口识别出 SSH/数据库 | 进 [06 章](06-nse.md) 用对应脚本做进一步信息收集（注意风险等级） |

## 5.4 `-O`：操作系统识别

### 命令

```bash
nmap -O <目标IP>
```

### 适用场景

需要判断目标是 Windows 还是 Linux/Unix，用于决定后续用哪类脚本、看哪类漏洞。

### 原理

TCP/IP 协议栈在不同操作系统上的实现细节不同（初始 TTL、TCP 窗口大小、IP ID 生成方式、TCP 选项顺序、ICMP 错误消息格式等）。Nmap 收集十几种这类"指纹"，与内置的 `nmap-os-db` 比对。

**这就是为什么 `-O` 需要"至少一个开放端口 + 一个关闭端口"**：没有关闭端口就拿不到对"无服务响应"的采样，指纹不完整。

### 示例

```bash
sudo nmap -O -p 22,80,443,1 192.0.2.10
```

### 示例输出

【待补充示例输出】建议补充：对一台 Linux 靶机执行 `-O` 的完整输出底部，展示 `Device type`、`Running`、`OS CPE`、`OS details`、
`Network Distance` 这几行的层次关系，以及低置信度时 `Aggressive OS guesses` 的形态。

输出底部形态：

```text
Device type: general purpose
Running: <厂商> <内核系列>
OS CPE: cpe:/o:<厂商>:<产品>:<版本>
OS details: <具体版本描述>
Network Distance: 1 hop
```

低置信度时：

```text
Aggressive OS guesses: <系统A> (<置信度>%), <系统B> (<置信度>%), ...
No exact OS matches for host (test conditions non-ideal).
```

### 结果判读

| 你看到 | 含义 |
| --- | --- |
| `OS details: ...` | 明确匹配，可信度较高 |
| `Aggressive OS guesses: ... (95%)` | 多个候选项 + 置信度，**不是确定结论** |
| `No exact OS matches` | 没匹配上，可能虚拟化/容器/防火墙干扰 |
| `Too many fingerprints match this host` | 指纹无区分度，常见于云主机与容器 |
| 完全没有 OS 段 | 条件不足（缺 open/closed 配对），或权限不够 |

**判读原则**：`-O` 的结论永远带概率。**报告里写"疑似 Linux 4.x（置信度 95%）"，不要写"目标是 CentOS 7"。**

### 注意事项

| 项 | 说明 |
| --- | --- |
| 权限 | 需要 root（原始套接字） |
| 前提 | 至少 1 个 open + 1 个 closed 端口；`-p` 里故意加一个大概率关闭的端口（如 `1`）能提高成功率 |
| 准确度影响因素 | 虚拟化、NAT、容器、负载均衡、防火墙都会削弱指纹 |
| 隐蔽性 | `-O` 会发非常规组合的包，**极易被 IDS 标记** |
| 常见误判 | Linux 与 Android、FreeBSD 与 macOS、Windows 各版本之间经常互相误判 |

### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 识别模糊 | 加 `--osscan-guess` |
| 想减少探测 | 加 `--osscan-limit` |
| 完全识别不出 | 放弃 `-O`，从服务版本反推系统（如 `OpenSSH` 版本、`Server` 头） |

## 5.5 操作系统识别微调

### 5.5.1 `--osscan-guess`（激进猜测）

#### 命令

```bash
nmap -O --osscan-guess <目标IP>
```

#### 适用场景

默认 `-O` 给出 `No exact OS matches`，但你仍然想要一个"最像的候选列表"。

#### 示例

```bash
sudo nmap -O --osscan-guess -p 22,80,443,1 192.0.2.10
```

#### 示例输出

【待补充示例输出】建议补充：默认 `-O` 无匹配、加 `--osscan-guess` 后出现 `Aggressive OS guesses` 列表的对照输出。

#### 结果判读

会把**置信度较低的候选系统也列出来**，形如：

```text
Aggressive OS guesses: <系统A> (92%), <系统B> (88%), <系统C> (85%)
```

#### 注意事项

> [!WARNING]
> 这是"猜测"，不是"识别"。**候选列表越长，越说明没有可靠结论。** 只取第一条写报告是常见错误。

- 与 `--osscan-limit` 语义相反，不要同时用。
- 猜测结果**不能作为漏洞判断依据**——不能因为"猜是 Windows Server 2008"就去试 MS17-010。

#### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 候选里有一个置信度明显高（>95%） | 记录为"疑似"，继续用服务版本交叉验证 |
| 全是 80% 上下 | 视为未识别 |

### 5.5.2 `--osscan-limit`（限制探测范围）

#### 命令

```bash
nmap -O --osscan-limit <目标网段>
```

#### 适用场景

扫一个网段时，**只对"有开放端口且有 1 个关闭端口"的主机做 OS 探测**，跳过明显没戏的目标，省时间。

#### 示例

```bash
sudo nmap -O --osscan-limit -F 192.0.2.0/28
```

#### 示例输出

【待补充示例输出】建议补充：一个 `/28` 网段中，部分主机有 OS 段、部分没有的输出，说明"没有 OS 段 = 条件不满足被跳过"，而不是"识别失败"。

#### 结果判读

被跳过的主机**不会输出 OS 段**，也不会报错。这是一种"静默跳过"，容易让人误以为探测失败。

#### 注意事项

- 只在**扫描多个目标**时有意义，单目标加它基本无用。
- 它省的是时间，代价是**覆盖率**。

#### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 需要某台主机的 OS 但被跳过了 | 单独对它跑 `-O`（不加 `--osscan-limit`） |

## 5.6 `-A`：一把梭的代价

### 命令

```bash
nmap -A <目标IP>
```

### 适用场景

**只有一种情况该用**：你在自己的靶场里，想快速拿到"能拿到的全部信息"，且不在乎时间与噪音。

### 等价于

```text
-A = -sV（版本探测） + -O（系统识别） + -sC（默认脚本） + --traceroute（路由追踪）
```

### 示例

```bash
sudo nmap -A -p 22,80,443 192.0.2.10
```

### 示例输出

【待补充示例输出】建议补充：`-A -p 22,80,443` 的完整输出（含 OS 段、脚本段、`TRACEROUTE` 段），用于展示"一个命令产出四类信息"的结构，以及它到底有多长。

### 结果判读

输出会包含四块内容，按出现顺序：

1. 端口表（含 `VERSION` 列）
2. 脚本输出（`|_` 开头的行）
3. `OS and Service detection performed` 之后的操作系统段
4. `TRACEROUTE` 段（网络距离与路径）

### 注意事项

> [!WARNING]
> **`-A` 不是"更好的扫描"，它是"四个高噪音操作打包"。**
>
> - 默认脚本集（`-sC`）会发起大量 HTTP 请求、TLS 握手、SMB 查询；
> - `-O` 会发非常规 TCP 组合；
> - `--traceroute` 会发 TTL 递增的包；
> - 三者叠加，在任何有 IDS 的环境里都是**教科书级别的扫描特征**。

| 场景 | 该不该用 `-A` |
| --- | --- |
| 自己靶场、时间充裕 | 可以 |
| 客户生产环境、有 SOC 监控 | **不要**。拆成 `-sV` → `-sC` → 单独脚本，逐级确认 |
| 大批量网段 | 不要，慢到不可用 |
| 写报告要"完整" | 不要。`-A` 输出里 80% 是噪音 |

### 下一步决策

| 情况 | 下一步 |
| --- | --- |
| 想控制噪音但保留信息 | 拆开：`-sV` 先跑，再 `-sC -p <已确认端口>` |
| 脚本结果里有 `VULNERABLE` 字样 | **停下**。不要自行验证，先看 [06 章](06-nse.md) 的风险说明与 [10 章](10-legal-and-safety.md) |

## 5.7 输出怎么读：一个完整例子

把各段拼起来看，一台主机的完整"体检报告"结构是：

```text
Nmap scan report for <目标IP>            ← ① 目标
Host is up (0.00042s latency).           ← ② 存活与延迟
Not shown: 997 closed tcp ports (reset)  ← ③ 被隐藏的端口统计
PORT    STATE SERVICE  VERSION           ← ④ 端口表
22/tcp  open  ssh      <产品名> <版本>    ←    每个开放端口一行
80/tcp  open  http     <产品名> <版本>
443/tcp open  ssl/http <产品名> <版本>
|_http-title: <页面标题>                  ← ⑤ 脚本输出（-sC 才有）
Service Info: OS: Linux; CPE: ...        ← ⑥ 服务附加信息
OS details: <系统描述>                    ← ⑦ 系统识别（-O/-A 才有）
Network Distance: 1 hop                  ← ⑧ 路由距离（--traceroute 才有）
TRACEROUTE                               ← ⑨ 路由详情
```

**注意第 ③ 行**：`Not shown: 997 closed tcp ports (reset)` 说明另外 997 个端口是 `closed`。如果这一行写的是 `filtered`，
含义完全不同——那说明有防火墙。**这一行经常被忽略，但它是判断"有没有防火墙"的最快入口。**
